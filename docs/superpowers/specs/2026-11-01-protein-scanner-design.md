# Protein Scanner: hackathon prototype design

**Status:** revised for the user's latest scope decision; review this revision before implementation. Target a mobile-first prototype at a public URL by November 4. Live Meta spending and deployment require separate approval and remain unverified.

## Goal and scope

Help a judge identify a packaged food and shelf price, correct the results, and compare protein per dollar and protein per 100 kcal. Prioritize a robust scanner and a simple device-local food diary. A judge without a camera can upload a photo, enter values manually, or use a visibly labeled example. There are no shared listings, ratings, price observations, or shared database. The prototype is not a diet recommendation, live pricing service, or medical tool.

**Approaches:** The chosen Muse-assisted approach interprets images while deterministic code calculates from attributable or user-entered values. Manual entry and barcode lookup alone are more predictable but lack the requested assisted scanner; full retailer integrations would introduce avoidable access and schedule risk. Optional marketplace links are plain searches, not prices or offers.

## Architecture and boundaries

- **Mobile web client:** camera preview, upload, manual entry, confirmation, results and a browser-local diary. Camera access requires a secure context; the public URL must use HTTPS. No app installation is required.
- **Application server:** validates bounded image requests, applies single-process in-memory rate controls, and sends images to Muse only after explicit consent. The developer supplies `MUSE_API_KEY` server-side: use an ignored `.env.local` for local development and hosting environment variables for an approved deployment. The model is disabled unless `MODEL_ENABLED=true` **and** the key is present. Neither value is exposed in client code or logs. Server-side OFF lookup may run independently of Muse.
- **Nutrition lookup:** Open Food Facts (OFF) is the primary attributable food database. Barcode lookup or search returns candidates for explicit user selection; preserve product ID, source link and available basis/unit information. Visible nutrition labels and user-entered values are alternatives, marked with their actual provenance. Muse may transcribe a visible label but must not supply missing nutrition values from memory or inference. Blank or uncertain fields stay unavailable until supported or entered.
- **Data boundaries:** Image bytes, including sampled frames and the selected image, are processed transiently in memory and never stored by the application. The selected frame can remain in browser memory briefly for review; release it when no longer needed. No application database or image storage is used. Diary entries persist only in the user's browser/device, not on the server.
- **Calculations:** pure deterministic code uses only confirmed values and compatible units. Neither Muse nor a marketplace supplies computed nutrition facts.

## Scanner and confirmation flow

1. Landing page offers **Scan**, **Upload photo**, **Enter manually**, and **Try example**. Before any image upload or analysis, explain that camera samples or an uploaded photo are sent to Meta, that the app does not store images, and that Meta's processing and retention are subject to its applicable terms. Require one explicit, unselected opt-in for Meta transmission. Declining or withdrawing consent prevents future image submissions; it cannot undo data already sent to Meta. Manual entry, OFF lookup and the example need no image consent. Do not imply a provider training opt-out or other unverified retention guarantee.
2. With consent and camera permission, display a preview and capture sampled still frames at a configurable bounded interval. A client has at most one Muse request in flight; no queued frames accumulate. On a response indicating both an item and shelf price, automatically select that frame as a candidate and stop sampling. If only one is detected, stop sampling, present the candidate and prompt for the missing item or price. Neither result is assumed correct; provide retry, upload and manual entry. When neither is detected, continue bounded sampling until the user stops or a rate limit is reached. Do not promise instant detection or a latency target until measured.
3. Upload follows the same consent, analysis and review path for one chosen image. Manual entry requires no image or model. The example uses explicitly labeled fixture content and calculations and is not shown as a live lookup or price.
4. Review shows the in-memory image/crop where available, detected item and price as editable candidates, currency and quantity/basis, and nutrition source and fields. The user selects or rejects an OFF match; an ambiguous or absent match cannot silently become the confirmed item. Allow correction of all extracted values and manual nutrition entry, including package amount and serving basis. Explicit confirmation precedes calculated results. A model-transcribed label is attributed to the visible label, and uncertain text is flagged for correction, not presented as verified.
5. Show available metrics with units, inputs, source and limitations; unavailable values explain what is missing or incompatible. User can correct inputs and recalculate. An explicit action adds a selected food and quantity to the local diary. An optional marketplace search link uses the confirmed product name; it is clearly labeled as a search and does not display or store retailer prices.

**Muse contract:** send only the bounded image needed for the current attempt; request a strict JSON object with optional item description/barcode, price amount/currency/price basis, and only nutrition/quantity values visibly present, plus uncertainty or absent fields. Server validates the response schema and numeric ranges; malformed, contradictory, unsupported, or ambiguous fields become unavailable rather than guessed. OCR quality, structured output and latency remain unverified until separately approved live testing. Do not retry endlessly: offer an explicit user retry after a failed attempt.

## Quantities and calculations

Keep numeric amount, unit, basis, currency and provenance separately. Resolve product identity and price to the same explicitly confirmed package/quantity. Permit a price per unit weight only when its weight unit, purchased quantity and nutrition basis can be safely converted; otherwise mark protein per dollar unavailable. Never equate milliliters and grams without a supported, attributable conversion. Currency is displayed, never silently converted. A multi-pack or serving is normalized only when count/size and label basis are known; otherwise ask for correction or show unavailable.

- For a confirmed package with protein `p` grams and price `c` in a currency, protein per currency unit is `p / c`, only if `c > 0` and both values cover the same package. Display `g protein / $` only for USD; otherwise name the currency. A supported zero protein numerator is valid.
- For protein `p` grams and energy `e` kcal on the **same quantity basis**, protein per 100 kcal is `100 * p / e`, only if `e > 0`. Negative, non-finite, missing, or incompatible inputs are invalid/unavailable; positive denominators are mandatory. Round only for display and retain inputs for recalculation.
- Example: a 200 g package at $4.00 with 10 g protein and 100 kcal per 100 g contains 20 g protein and 200 kcal. It yields **5 g protein/$** and **10 g protein/100 kcal**. If package mass is missing, the first metric is unavailable; the second remains 10 g/100 kcal because both nutrition values share the per-100-g basis.
- OFF's `energy-kcal_100g` is kcal per 100 g; `energy_100g` is in kJ and must not be labeled kcal. Convert kJ only with an explicit, tested conversion and known matching basis, or leave kcal unavailable. Missing source fields are not zeros.

## Device-local diary and search links

After confirmation, the user selects an amount on a compatible basis and saves a dated entry locally. Display recorded food, amount, available protein and energy, plus totals only for entries with compatible known values; clearly mark incomplete totals. Users can remove local entries. Explain that clearing browser data or changing devices can lose the diary and report local save failures. Entries contain no image and no stored price. They are never presented as shared or synchronized.

Marketplace links, if offered, contain the encoded confirmed product name and open a retailer/marketplace search. They are not offers, live prices, or price observations. No retailer scraping or retailer API access is assumed.

## Privacy, reliability and cost controls

Process images only in memory on client and server; do not write image bytes, thumbnails or derived image files to disk, browser persistent storage, server storage, logs, or caches. Send `no-store` responses for image operations and release temporary buffers and preview URLs after use. Limit image byte/pixel sizes, validate actual media type and decoding, and treat arbitrary uploads and extracted text as untrusted. Strip EXIF/location metadata before transmission where feasible; explain any unsupported path rather than promise anonymization. Images can contain sensitive information. Meta receives submitted images, including sampled camera frames, under its own applicable terms; the app's non-storage policy does not guarantee Meta's retention or erasure behavior.

The model route is off unless `MODEL_ENABLED=true` and `MUSE_API_KEY` is present; these are necessary configuration, not authorization to spend. Enforce bounded sampling, one in-flight request per client, request size, concurrency, timeout and response size, plus conservative **in-memory, per-client and per-process** request limits. The operator can disable new calls by changing `MODEL_ENABLED` and restarting/reconfiguring the process; already in-flight requests may finish. Rate counters reset on restart and are not coordinated across processes, serverless instances or hosts. Client identity can be unreliable behind proxies. These are abuse-reduction measures, **not a global limit or guaranteed billing hard cap**; provider pricing and accounting determine charges. The available budget is $150 in Meta API credits; no live use or credit expenditure is authorized by this spec. Choose limits only after reviewing pricing and receiving separate spend approval.

Denied/unavailable camera, insecure context, timeout, malformed model response, unrecognized item/price, OFF no-match/outage, conflicting units, invalid input, local diary failure, model disabled, and exhausted process limits each show a plain-language state with a relevant retry or manual alternative. The app remains usable without camera or Muse. Do not silently retry, fabricate values, or lose confirmed input on network/provider failure. Respect OFF attribution and applicable data-use terms before publication.

## Acceptance criteria

1. On a suitable phone over HTTPS, consenting users can attempt bounded camera sampling; when a response has both item and price candidates it stops and opens review. With only one candidate, the UI prompts for the other. The user can edit both, reject an incorrect product match, and continue manually after failure.
2. Without a camera, a judge can upload with Meta-transmission consent, enter data manually without consent, or run the labeled example. Camera denial, lack of consent, model failure, and a disabled/limited model route do not prevent manual calculation.
3. Nutrition is traceable to an OFF record, a visibly read label or user input, with basis and units shown; unsupported or missing numbers remain unavailable. Calculations require matching quantities and valid denominators, distinguish kcal from kJ, and handle unsafe weight/volume conversions as unavailable.
4. A confirmed food can be added to a persistent device-local diary, with incomplete totals clearly labeled. No diary synchronization or shared data is implied. Any marketplace link is labeled as a search and displays or stores no price.
5. The app asks for one explicit Meta-transmission consent before image analysis. It does not store images; the key stays server-side, and model calls are disabled unless both required configuration values are present. Single-process rate limits and their reset/multi-instance limitations are disclosed; no guaranteed billing cap is claimed.
6. The public-URL demonstration is only complete after separately authorized hosting is configured and verified; no deployment or expenditure is implied by approval of this spec.

## Targeted verification and approvals

- Unit-test schema rejection, missing/zero/negative/non-finite values, mixed bases, multi-pack quantities, compatible and incompatible weight pricing, kcal versus kJ, and the numerical examples above. Test that model output cannot populate an unsupported nutrition field.
- With mocked Muse/OFF responses, cover both-present, item-only, price-only, no-result, bad JSON, timeout, no-match, incorrect match correction, consent rejection/withdrawal, upload, manual entry, disabled configuration and in-memory rate exhaustion. Verify one in-flight request, bounded sampling and honest errors. Assert no image is persisted or logged, including selected frames; inspect client/server paths and response cache settings.
- Test malformed, oversized and misleading image types; verify supported metadata stripping, local diary persistence/reload, incomplete totals, storage denial, search-link labeling, keyboard access and camera permission errors. Tests do not prove provider-side erasure or legal compliance.
- After separate approval for spending and provider setup, perform a bounded live Muse test with consented sample images; record actual detection quality, schema behavior, latency, request count and charges where observable. A mock pass is not live-model validation.
- After separate approval for hosting/deployment, test the public HTTPS URL on a real phone with camera permissions and on a camera-free browser via upload/demo. Verify OFF attribution, local diary, usable search links and failure recovery. Record actual results and limitations; do not claim real-phone or public-service verification based only on local tests.
